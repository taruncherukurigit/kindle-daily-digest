Two nodes, one link

$ traceroute digest.pipeline

One run, hop by hop

1
schedule-trigger
Fires twice a day, 6am and 6pm. Nothing runs outside these two windows.
2
freshrss-auth
n8n logs into FreshRSS's Reader API, pulls unread items across all 18 categories, caps any one feed at 30, marks everything fetched as read.
3
source-rank
A fixed list of primary sources sorts first. Everything else sorts by freshness. No model in the loop.
4
assemble
Near-duplicate titles collapse into one. Full text pulled through the receiver. Each article gets an anchor id and a spot in the Quick Skim index.
5
kindle.amazon.com
pandoc renders the epub, a dated copy gets archived and it lands in your Send-to-Kindle inbox.

Why it works this way

[reliability]

No AI calls anywhere in the run path. An earlier version used Claude Code for search and synthesis, and a single run could burn through a usage window and fail silently. This version replaced every judgment call with a fixed rule: source weighting, per-feed caps, cross-category dedup, freshness sort. Nothing here can fail from a usage cap, because nothing here calls a model.

[capacity]

Per-feed cap, not per-category. One high-volume feed with hundreds of unread items could eat an entire category's budget by itself during testing. Capping the feed instead of the category keeps any single source from crowding out the rest, the same reason you would not let one interface saturate a shared uplink.

[navigation]

Quick Skim links jump inside the epub. An e-ink Kindle often has no working browser at all. Every article is a real heading with its own anchor id, so the index jumps straight to the full text already sitting in the file. A small second link still points out to the source for anyone reading on something with a browser.

[scope]

No images. RSS enclosure tags only covered a fraction of articles, and the text-extraction endpoint never returns images at all. Shipping a feature that worked for some entries and silently failed for the rest was worse than not shipping it.
